工程实践 · 2026-09-16

Claude Code 1M 上下文配置实录

一次完整的排查记录:让 Claude Code 桌面 App 的自动压缩阈值从 200K 提到接近 1M。 每一步都给出现象 → 根因 → 操作,写给想复刻的人,也写给接手维护的自己。已验证生效。

一句话结论

桌面 App 的推理配置文件里,模型条目加上 "supports1m": true(可加 "prefer1m": true 设为默认),模型选择器就会出现 1M 变体,客户端随之按 1M 计算压缩阈值。再配合 ~/.claude/settings.json 顶层 "autoCompactWindow": 900000 留安全余量。

背景

  • 环境:Windows 11,Claude Code 桌面 App(Code 标签页),走本地网关转发请求。
  • 症状:会话每到 200K token 就触发 auto-compact,长任务被反复压缩,体验很差。
  • 关键实测:向网关后端直接发约 93 万 input tokens 的请求,正常返回 → 说明后端装得下接近 1M,200K 纯粹是客户端自己的保守认知。

根因链:为什么改了很多处都没用

客户端的窗口解析逻辑可以总结成这两行:

实际压缩阈值 = min(autoCompactWindow 设置, 客户端相信的模型窗口)

客户端相信的模型窗口:
  1. 模型名以 [1m] 结尾 → 直接按 1M 计算        ← 最强,无附加条件
  2. 配置里模型声明了 supports1m → 选择器提供 1M 变体,
     选中后模型名即带 [1m] 后缀
  3. 否则:模型表里明明写着 1M,也会"降级相信"为 200K
     ← 这就是 200K 压缩的根源

这个 min() 意味着:只调 autoCompactWindow 没有用,必须先让客户端"相信"模型窗口是 1M。

走过的弯路(都无效,别再试)

尝试为什么无效
settings.json 里模型名加 [1M] 后缀桌面 App 托管模式会把环境变量里的模型设置覆盖为空,不生效
ANTHROPIC_MODEL 指定带 [1m] 的模型名优先级:App 选择器传入的模型 > 环境变量 > settings 的 model。App 传了裸名,env 被压掉
请求头加 context-1m beta header只影响请求头,不影响客户端对窗口大小的认知
网关代理层改写模型名加 [1m]模型名由客户端解析,网关改写对客户端不可见
"autoCompactWindow": 900000 单独使用被 min() 钳到 200K(但与 supports1m 组合后有效,见下)

操作步骤(复刻指南)

第 1 步:确认后端真的装得下大上下文(可选但强烈建议)

先探测后端的真实容量,避免把"压缩太频繁"的问题变成"请求直接报错"。用 python 发一个大请求(Windows 下别用 curl,TLS 会挂):

python - <<'EOF'
import json, random, urllib.request
random.seed(42)
words = [f'w{i}{chr(97+random.randint(0,25))}' for i in range(5000)]
text = ' '.join(random.choices(words, k=210000))   # 约等于 93 万 token
body = json.dumps({'model':'claude-sonnet-5','max_tokens':8,
    'messages':[{'role':'user','content': text + '\n\n只需回复:ok'}]}).encode()
req = urllib.request.Request('http://127.0.0.1:<port>/v1/messages', data=body,
    headers={'content-type':'application/json','anthropic-version':'2023-06-01'})
r = urllib.request.urlopen(req, timeout=300)
print(json.loads(r.read()).get('usage'))   # 看 input_tokens 是否远超 200K 且返回 200
EOF

返回 200 且 input_tokens 达到几十万 → 后端支持,继续;报 4xx → 后端真的只有 200K,到此为止(这是后端套餐问题,客户端无解)。

第 2 步:找到 App 的推理配置文件

桌面 App 的配置目录下有一个 configLibrary/,其中 _meta.json 的 appliedId 字段指出当前生效的配置文件(一个 uuid 命名的 .json)。生效文件改之前长这样:

{
  "inferenceProvider": "gateway",
  "inferenceGatewayBaseUrl": "http://127.0.0.1:<port>",
  "inferenceModels": [
    { "name": "sonnet" }
  ]
}

第 3 步:备份并修改模型列表

先复制一份备份(如 原文件名.json.bak),然后把 inferenceModels 改成:

"inferenceModels": [
  {
    "name": "claude-sonnet-5",
    "supports1m": true,
    "prefer1m": true,
    "anthropicFamilyTier": "sonnet",
    "isFamilyDefault": true
  },
  {
    "name": "claude-haiku-4-5",
    "anthropicFamilyTier": "haiku",
    "isFamilyDefault": true
  },
  {
    "name": "claude-opus-4-8",
    "supports1m": true,
    "anthropicFamilyTier": "opus",
    "isFamilyDefault": true
  }
]

各字段含义:

字段作用
name必须是网关端点接受的确切模型 ID。"claude-sonnet-5[1m]" 是 supports1m: true 的等价简写
supports1m核心开关。给该模型在选择器里加一个 1M 上下文变体。只对确认支持 1M 的部署勾选
prefer1m该模型是默认模型时,1M 变体作为选择器默认选中项(用户仍可切换)
anthropicFamilyTier告诉 App 该条目顶替哪个档位(haiku/sonnet/opus/fable),裸别名(如 sonnet)才能解析到它
isFamilyDefault同档位多条目时的默认赢家

第 4 步:settings.json 加安全余量(可选)

~/.claude/settings.json 顶层加:

"autoCompactWindow": 900000

模型窗口变成 1M 后,实际压缩阈值 = min(900000, 1M) = 90 万——比顶满 1M 留约 10% 余量,避免贴边报错。不想要余量可省略此步(阈值即 1M)。

第 5 步:完全重启桌面 App

  • 托盘图标也退出,再重新启动(配置在启动时读取)。
  • App 正在运行时改配置文件,退出时可能被内存态覆盖回去。改完立刻重启;如果发现文件被打回原形,改走 App 设置界面:在模型列表里添加模型并勾选 "Offer 1M-context variant"(对应 supports1m)和 "Default to 1M context"(对应 prefer1m),效果相同。

验证

  1. 新开对话,模型选择器应出现 1M 变体(或默认已选中)。
  2. /context 看 Tokens 分母是否为 1M。注意:必须在新会话里看,旧会话是启动时读的配置,永远显示旧值。
  3. 实际使用中观察:不再在 ~167K(200K × 83%)附近触发 compact。

回滚

  • 还原配置目录里的模型列表(用备份覆盖回去)。
  • 删掉 settings.json 里的 autoCompactWindow 行。
  • 重启 App。

这次排查学到的

  • 先测后端,再怪客户端。93 万 token 探测请求直接把"瓶颈在哪"这一半问题定死了——剩下的一切排查才有方向。
  • 工具链的每一层都可能"好心办坏事"。客户端的 min() 钳制是保护,但保护性降级如果没有开关暴露出来,就成了排查黑洞。
  • 配置的读取时机和优先级比配置内容本身更重要。同一个配置项,放在 env、settings、App 选择器三个位置,结果完全不同——先搞清楚谁覆盖谁,再动手改。
