Agent Skill 框架架构五问

结合一次 agent skill 平台的实践——完成两个 skill(模糊报障转标准运维工单、个性化教育游戏策划)的创建、上传、运行与迭代——对五个架构问题的回答。 文中的「创建器 / 框架 / 运行时」指一个典型 skill 平台的三层组件。

问题一:create skill 的稳定性从哪来,架构会有哪些组成部分

企业给一段模糊的需求,期望得到一个能反复跑的东西。这件事用一次对话做不到:对话换个 session 就没了,模型两次跑的结果也不一样,做完了也没有标准判断"算不算做完"。实践里都遇到过:创建中断后卡死在生成流程,另一个 session 接不上;出现过输出退化;像教育游戏策划这种没有标准答案的产出,只能手写检查表来验收。所以 create skill 做的事情是把一次对话沉淀成一个有结构、有验收标准、能交接的项目。脚本能自己复用,但只有项目能交接给别人。

稳定性来自契约加状态机。契约门管输入输出是否符合声明,结构门管目录是否符合规范,流程门管流程没走完就想跳步。三道门的覆盖面不均匀。运维工单 skill 的数字:15 条批量输出,结构、公式、明文泄漏的问题 0 处,优先级和参考答案的一致率 8/10。前者契约管得到(字段名、类型、取值范围都声明了),后者管不到(定 P2 还是 P3 是业务判断)。契约覆盖到哪里,稳定性就到哪里。

契约管不到的部分,三种处理办法:

  • 把判断改造成检查。优先级定级显式写成规则表、置信度写成公式让它可以复算。这个做法把契约的边界往外推了。
  • 显式确认门。主观取舍交给人拍板,教育游戏 skill 的每阶段停等属于这种。
  • AI 评判当辅助。效果存疑——它把不确定性转移了,没有消除。实践中有模型自检失灵的例子:从平台能力清单外推出一个新用法,自检里写"无虚构"。帮忙找漏可以,作为最终判定不可靠。

还有一种中间状态。两个 skill 都是剧本模式(单 agent 节点加一份自然语言剧本),流程门在这种模式下是约定不是机制:剧本里写了"每阶段停等确认",但状态机看不到剧本,只能靠 agent 自觉。结构校验和契约校验它一样有,缺的是过程可见和行为可测。补的办法:把约定里可数的部分变成可核对的数字。剧本带一个结构化的阶段声明,校验器就能做交叉核对——剧本声称的阶段数和输出契约要求的阶段记录数对不上,是真矛盾(多半是改了一边忘了另一边),报错;插件声明用脚本执行但实际没有脚本节点,报错。数量核对不需要理解语义,数一数就行,能抓住"两边说好的约定不一致"这一类问题。它不会把约定变成机制,阶段门还是事后校验,不是事前阻止。

架构组成。按能力划四块,依赖顺序:定义(什么叫合法的输入输出和流程)、构造(怎么从定义生成真实项目)、执行(怎么跑起来、怎么保证每步合规)、治理(怎么验证、打包、追溯)。但这轮报的三个 bug——沙箱静默失败、拒绝标记丢失、目录越界——没有一个属于这四块,全在授权边界和失败可见性上。所以还要两块横切的:

  • 运行环境与授权边界:能读哪些目录、能写哪些文件、越界怎么报、失败怎么标。这层在所有包脚下的平台层,但三个 bug 的原因相同——边界和失败状态对用户和 agent 都不可见。
  • 可观测性:校验结果、运行状态、产物版本。问题四里"校验已经发生了但看不见"就是这块的缺失。

问题二:创建器、框架、运行时三层各自负责什么

按四块能力去对三层,有个错位:定义、构造、治理都在框架,执行在运行时,创建器在能力清单里没有对应。错位说明切分轴不一样:四块能力回答系统需要什么本领,三层回答谁提供本领、谁使用本领。创建器不提供新本领,它消费框架的规范和运行时的驱动,把需求推导成合法 skill。

职责:

  • 框架:契约、契约的表达语言、骨架生成、静态校验加回归测试、审计、打包导出、档案和账本这类证据结构。边界很明确——不含流程知识,没有"先做什么再做什么"。
  • 运行时:状态机驱动、skill 库(列表、导入、导出)、对外接口。
  • 创建器:推导流程,六个节点加档案加发布。造 skill 的流程本身就是一个 skill,有自己的清单文件和节点目录,跟它造出来的东西结构相同。

运行时有两条容易被漏掉的职责。一是 agent 节点委派主 agent 时的失败路径。"把任务交给主 agent、等文档交回来"省略了很多东西:节点输出不符合契约会打回重试,重试有次数上限,超限进 blocked 终态,不是无限等。超时怎么办、主 agent 拒答怎么办,这些边界条件决定停等机制可不可靠。二是 skill 库的版本管理。Run 结果不记录 skill 版本,跨模型对比时分不清差异来自模型还是版本漂移,只能靠目录名人工区分。库是运行时管的,"这次 run 用的是哪个版本"也应该是它的账。

三层设计里最关键的一条是声明与驱动分离:skill 只声明有哪些节点、每步输出契约是什么,运行时按序推进、委派、校验、打回或放行,框架定义声明怎么写。skill 里没有循环和调度逻辑。这样 skill 可以很短;引擎修一次所有 skill 受益;也只有 skill 只需要声明时,"造 skill 的流程"才能也用声明表达,创建器才能自己也是一个 skill。反过来如果 skill 自带引擎,做事的人和判事的人就是同一个——校验输出的人和产出输出的人是同一个东西;执行链出问题,同样的补丁要在每个 skill 上打一遍,而不是改运行时一处。

问题三:创建器和框架之间是什么关系

框架不依赖创建器;反过来创建器大量使用框架:骨架生成、校验器、错误类型、契约类型。依赖是单向的。

定性靠一个证据:创建器的发布节点在发布之前,调用框架的校验器校验自己刚造出来的 skill。创建器的质量标准不是自己定的。所以框架是规范加执法者,创建器是规范约束下的推导过程。类比编译器:框架是语言规范加类型检查器加代码生成器,创建器是编译器前端,前端不定义语言,只保证输出能被后端接受。"创建器是框架的上层封装"只对一半——封装暗示可以绕开,实际上它的产物必须过框架的校验;"两者并列"不成立,创建器直接调框架的校验器。

错误处理分三种情况:

  • 草稿不满足校验(发布节点):不是重做。把差距清单照进 prompt,模型在当前节点补齐。同一个校验器用两次,提交前当提示,发布管线里当门。
  • 骨架生成本身失败(定义节点):重做。清空草稿,抛错让模型改定义重交。
  • 节点内部处理失败:抛错即反馈,节点级重试,不是整体重来。

提示用的校验和门用的校验如果是两套代码,早晚会分叉,这里用同一个校验器就没有这个问题。

可以改进的地方:校验器报错是自然语言,没有机器可读的分类,"该回卷到哪个节点"写在提示里让模型自己判断。错误分类还有第二个用途:决定回卷时保留什么。契约问题回卷定义,实现问题只回卷实现,定义和派生层都不用动。这跟问题五的派生层、手写层是同一件事——回卷的粒度就是增量修改的粒度。

还有一个设计:创建器自己是 skill,框架的规范每天被一个最复杂的用户消费。创建器有六个节点、十来个过程 schema,还要落档案和证据,对规范的使用程度超过任何普通 skill。规范哪里不好用,最先在创建器身上暴露出来,相当于给规范配了一个持续的内部压力测试。

问题四:契约即测试——需要对不同 schema 各生成校验器吗

不需要生成,一个通用解释器加每份 schema 一份声明就够了。校验器是通用的:接收任意 schema 和任意数据,当场比对返回错误清单,不产生中间产物。生成方案的问题在产物上:生成器产出的是代码,代码会过期、会和源不一致、要跟着改;解释器没有产物,不存在过期问题。份数上,生成要维护 N 份,解释器一份。

通用校验器已经存在,每次 run 都在用。真正的缺口在两个地方。

一是契约的表达能力。现在只能声明结构——字段名、类型、必填、枚举、范围,声明不了业务规则。拿运维工单 skill 实际查的项对照:JSON 结构、键完整性、取值合法性、多问题拆卡的结构,契约已经自动管了;跨字段算术(置信度公式复算)、内容语义(明文泄漏扫描)、覆盖完整性(追问是否覆盖缺失项)、业务判断(优先级定得对不对),管不了。教育游戏 skill 里有一条做得很彻底:输出契约声明"阶段门记录必须是 7 项、每项已确认字段必须为真","每阶段必须经用户确认"这条规则被完全形式化了,填 false 直接判失败。所以卡点不是契约语言不够强,是规则本身有没有被形式化。

二是校验结果的可见性。契约门失败会报错,成功时结果不显示,判断这次 run 是否满足契约还是要自己读输出。校验已经发生了,只是看不见。

扩展契约的表达能力,思路是不另造一套声明语法,而是给契约里的特定字段挂一个受控的表达式求值器,让契约能写跨字段、跨文档的断言(比如"置信度等于基准值减去系数乘缺失字段数")。具体选哪种表达式语言是选型问题,需要单独评估,但有一条红线必须守住:表达式只能读本记录和声明的输入引用,不能调用工具、不能调模型,否则契约门自己变成不确定性来源,违反"做事与判事分开"。求值器应该是确定性的——同一份输入永远得到同一个判定,这样契约门才可靠。

判断标准:能形式化的判断放进契约,自动、每次 run 都查、跨 skill 复用;依赖个人经验的留在脚本或留给人。中间有灰色地带——有些经验能部分形式化。"信息不足时不许猜优先级"完全形式化做不到("信息不足"是语义判断),但"缺失字段非空则优先级必须为待定"能拦住大部分。对这类灰色地带,把能形式化的部分先形式化、剩下交给人工复核,也许是一个务实的中间态。

框架还会从输入契约自动派生边界用例:删掉每个必填字段、给每个可判型字段喂错误类型,要求必须失败,回归测试真的执行它们。实践时手写的三条负向用例,就是这件事的手工版。

问题五:脚手架做了什么,为什么大改会重建,增量怎么设计

脚手架的流程七步:校验参数(id 必须是 kebab-case,名称描述非空);检查目标目录,已存在且非空直接拒绝;写入整套骨架文件(根文件加六层目录);只建空目录(示例与资产层,内容留给作者);应用覆盖项(入口命令、输入输出契约);从清单文件生成契约镜像(清单是唯一事实源,镜像靠再生成保持同步);注入场景与示例。

大改定义会导致重建,原因不在"改定义"这个动作,在"改定义只能回卷到定义节点重跑"这条通路。定义节点定稿时立刻生成草稿目录,后续节点都在这个真实目录里写文件;脚手架的契约是目标目录非空就拒绝,重跑前必须先清空目录,重跑就成了清空整个草稿根再重新生成。根因:脚手架是只写不删、要求空目录的一次性生成器,不是同步器。

这个根因还有个副作用,在一个已完成的 skill 上可以直接观察到:剧本模式下骨架残留无用的占位文件。一个永远不会被调用的占位脚本,一个还指向它的入口命令,一个测试该占位脚本的占位测试,三者互相验证通过、回归全绿。这些不算 bug,没有契约被违反,skill 的创建、发布、运行全部正常。由它引出的一个更普遍的问题放在文末讨论。

增量修改分两档。最小可行版:给脚手架加 update 模式加文件级 hash。每个派生文件记录生成时对应的源 hash,hash 没变就不动,变了才重写,手写文件永远不碰。"改定义丢剧本"这个最大的痛点当场解决,而且不需要先搞清楚哪个源影响哪个文件。实现细节:hash 不能写进契约镜像文件里,会破坏镜像与清单逐字节一致的校验,用一份集中的 sidecar 记录文件到源 hash 的映射。完整版分为四步:文件分成派生层和手写层;用档案里的定义快照当基线算差异;只重算受影响的派生文件,手写文件打待复核标记;用校验器核对投影与源一致。完整版多解决两件事:模式切换时的残留清理,改了 A 该重算 B 和 C 的精确映射。代价:最小版不动脚手架的核心契约,完整版要把"非空即拒绝"拆成首次生成和投影同步两个操作。

还有一层是提这条建议时没想到的:增量的前提是源和产物在一起,但它们是分离的。源(定义)在创建过程的档案里,属于创建器;产物在 skill 库的目录里,属于用户。改定义变便宜了只方便创建阶段,用户想改已经发布出去的 skill,定义还是够不着——回卷工具只能回卷创建流程的节点,不能拿产物反向更新定义,用户改了产物之后定义就成了没人维护的旧账。改产物这条路本身是通的:导出、改文件、重新导入。导入是零信任管线,静态审计有严重问题或回归测试失败都会被拒。给用户一条改到源的路,有三个思路:

  • 定义跟着包走:包里放定义文件加同步工具。代价是两份源要同步,多一个分叉点。
  • 发布即冻结:发布后以产物为源,定义只作历史记录。代价是放弃"定义是唯一事实源"。
  • 双向同步:手改产物后校验报错,给两个选项——重新生成(丢弃手改),或把产物提升为新源(更新定义)。实现最复杂,最贴合真实工作流。

个人比较倾向第三个的简化版。完整答案是三步:分派生层和手写层,用定义快照当基线只重算派生文件,给用户一条改到源的路。

附录:一个门通过了,但它没在检查真东西

某个已完成的 skill 上有三个现象。

  1. 入口脚本 run.ts 是骨架生成的占位脚本,把输入原样回显,"请替换成真实实现"的注释都还在。这个 skill 走剧本模式,执行入口是 agent 节点,脚本永远不会被调用。
  2. 清单文件的入口命令还指向这个死脚本,那是骨架的默认值。清单契约强制要求入口命令非空,所以一个完全没有脚本的 skill 也必须声明一个。
  3. 骨架生成的占位测试:喂 {ping: 'hello'} 进去,断言那个占位脚本的 echo 输出。占位测试测的正是占位脚本,它永远通过。

它们都不算 bug,但第三个现象反映了一个问题。占位测试把"这个 skill 没有自动化测试"伪装成了"测试通过",从外面看不出来。导入管线本来有机制正确表达"无测试":遇到没有测试文件的 skill,审计结论标成需要人工复核。是那个占位文件把这个机制绕过去了。所以问题不是多了一个没用的文件,是一个门通过了,但它没在检查真东西。报过的沙箱问题(退出码 0 但命令没执行)也是同一种失效,换了一层。

把观察归纳一下,门其实分两种。一种检查"有没有":目录里有没有这个文件、tests 下有没有测试文件。拦不住占位,占位文件也是文件。另一种检查"对不对":契约镜像和清单是否逐字节一致、用例输入是否满足输入契约。

由此引出一个开放的设计问题:对于停留在"有没有"的那部分门,是让骨架按模式生成(从源头不留占位),还是给门补上可检查的关系(比如让测试代码引用用例文件里的用例)?

  1. 骨架要不要知道模式。脚手架现在不知道 skill 是脚本模式还是剧本模式,模式专有的文件在另一种模式下必然残留。把模式传进去让它生成不同的文件集是最干净的解法,但要改框架的接口;让创建器在覆盖时负责清理,改动小,但要维护一份该清理什么的清单。后者适合先做,前者是终态。
  2. 测试代码能不能和用例文件建立关系。测试代码现在的输入硬编码在代码里——骨架给的占位测试喂 {ping: 'hello'} 给一个只要 {text} 的 skill,这个输入本身就违反输入契约,但硬编码的输入不在任何校验范围内。用例文件不同,它里面的用例已经被契约校验过(每条 case 的输入必须满足清单的输入声明)。要求测试从用例文件读用例,等于给测试代码建立一条可检查的关系:它测的必须是本 skill 的合法输入。这拦不住"读了合法输入但断言写得很空",但能拦住"测试用的输入和这个 skill 完全无关"。
