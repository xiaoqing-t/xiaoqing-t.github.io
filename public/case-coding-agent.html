CASE 01 · AI AGENT

终端 Coding Agent

用 C 从零写一个能在终端里读代码、跑命令、改文件的 agent。真正的工作量不在调模型， 而在三件事：把工具调用收进一张注册表，把路径检查收进一道沙箱边界， 把无限增长的历史收进一套可替换的上下文策略。

  • 角色独立开发
  • 时间2026 秋 · 操作系统课设延伸
  • 规模约 2.3k 行 C
  • 仓库Project2-of-OS-2026-Fall ↗
稳定接口，可替换实现：agent 主循环不知道有哪些工具，也不关心历史用哪种压缩策略。

01

问题：每加一个工具，要改三个地方

Part 1 只有一个 bash 工具，调度就是一个 if (strcmp(name, "bash"))。等 Part 2 要加 read_file、write_file、edit_file， 同一个分支要在 agent.c 和 llm_client.c 里各写一遍： 前者负责执行，后者负责把工具描述发给模型。工具一多，两处描述就开始漂移。

第二个压力来自历史。每一轮都把旧的工具输出重新发一遍，上下文窗口、费用和模型的注意力 同时被吃掉。第三个压力在执行：一批三个互不依赖的读，被排成一队串行跑。

02

做法：把变化收进四个点

工具注册表

ToolDef 把名字、描述、参数 schema、执行函数和只读标记放在一起。 启动时 tool_register 注册，执行时 tool_find 查表。 新增工具 = 写一个 .c 文件，再在 tools_init() 里加一行； agent.c 和 llm_client.c 完全不用改。 read_only 不只是文档字段，它是执行器决定能不能并行的依据。

沙箱只有一道门

文件工具不能让模型读 /etc/passwd。 resolve_workspace_path 用 realpath 解开符号链接和 ..，再检查结果是否落在工作目录内；每个文件工具打开前都必须过这一道。 验证逻辑散在各工具里迟早会漏检，集中在一处才能保证一致。

执行器：只读并行，写入保序

一轮里模型可以返回多个工具调用。执行器按 read_only 拆批：只读的并发跑， 写入和编辑保持请求顺序；结果再按原顺序拼回去，模型看到的历史顺序是稳定的。 线程池来自课设的 shell / HTTP 底座，并发正确性用 ThreadSanitizer 验证。

上下文策略

ContextPolicy 只有三个字段：名字、should_apply、apply。 每次请求前 ctx_reclaim 按注册顺序走一遍，两种策略按代价从低到高排：

  • offload 先跑，无损。把旧的超长工具输出写到 .agent/offload/，历史里只留一个能被 read_file 找回的指针。
  • summary 后跑，有损。让模型把旧对话压成一条交接消息， 最近的 K 条原样保留。

阈值由 CONTEXT_WINDOW、OFFLOAD_THRESHOLD、 SUMMARY_THRESHOLD 三个环境变量控制。以后加第三种策略， 只需要实现两个函数再注册，agent 核心不动。

03

踩到的坑

  • HTTP 一直卡到 120 秒超时 curl 正常，自己写的 recv_all 却等不到结尾。 HTTP/1.1 默认持久连接，服务器发完响应不关连接；我们的代码靠读到 EOF 判断结束。 请求头加上 Connection: close。
  • 阈值设 0.9，却在 36% 就触发压缩 parse_env_int 把 0.9 解析失败，返回 0，再除以 100 还是 0。 浮点阈值改用 atof 单独处理。
  • 实现了 load_skill，模型却从不调用 模型不知道有这个工具。启动时扫描 skills/ 目录， 把技能列表注入 system prompt，工具才真正可达。
  • strncat 的截断警告 每次拼接前重算剩余空间 sizeof(buffer) - strlen(buffer) - 1， 给结束符留一个字节。 
const char *s = getenv("SUMMARY_THRESHOLD");
g_config.summary_threshold = (s && s[0]) ? atof(s) : 0.9f;

04

结果

2.3k行自研 C 代码
5个注册工具：bash / read / write / edit / skill
4/4端到端评测场景通过

评测脚本是黑盒的：起子进程、喂 prompt、按关键词判成功，超时 60 秒。 单次运行 4–6 秒，四个场景全部通过：

模块级有 CUnit 测试覆盖注册表、沙箱、执行器、卸载和摘要； 整机并发用 ThreadSanitizer 跑过。测试和评测都接在 Makefile 里， 换机器不用重新记命令。

05

反思

注册表、沙箱、上下文策略其实是同一件事：把会变的东西收进一个点，让主循环不变。 课程里把它叫作「稳定接口，可替换实现」；放到操作系统里，就是系统调用表、VFS 操作表 和设备驱动接口的同一形状。

还不够的地方也很明确：评测只有四个短任务、一个模型，证明不了真实代码库里的能力； token 统计是估算；还没有 streaming、失败重试、子 agent 和会话恢复。 下一步我会先把上下文决策记成可回放的日志——先能解释「这一步为什么被压缩」， 再谈压得好不好。

一句话：agent 的难点不是让它会调工具，而是工具的增减、历史的涨落都不改主循环。
